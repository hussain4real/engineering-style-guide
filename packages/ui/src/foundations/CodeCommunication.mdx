# Code Communication

Clear communication is part of engineering quality. MILAHA teams should use these standards for PRs, commits, review feedback, status updates, and handoffs. The source file is [`docs/guidelines/code-communication-guidelines.md`](https://github.com/hussain4real/engineering-style-guide/blob/main/docs/guidelines/code-communication-guidelines.md).

## Required PR Context

Every PR should explain:

- Why the change is needed.
- What changed.
- How it was tested.
- What risks, migrations, or rollout steps exist.
- Which requirements, tickets, documents, ADRs, or incidents are linked.

Example:

```md
## Summary
- Adds approval validation to the invoice workflow.
- Returns a documented error when an invoice is not pending.

## Testing
- pnpm run test:run
- Manual API check for `POST /invoices/:id/approve`

## Risk And Rollout
- Risk: low; validation only affects invalid transitions.
```

## Review Language

Use clear importance labels when helpful:

- `Blocking`
- `Should fix`
- `Suggestion`
- `Question`
- `Praise`

Review comments should be specific, respectful, actionable, and tied to code, behavior, requirements, or documented standards.

Example:

```text
Should fix: This route accepts a raw dict, so invalid payloads can reach business logic.

Impact: Consumers may receive inconsistent errors and OpenAPI will not describe the request contract.

Suggested direction: Add a Pydantic request model and cover invalid payloads in a router test.
```

## ADR Triggers

Create or update an ADR when a decision changes architecture, introduces a major dependency, affects security or compliance, creates a cross-team contract, or will be hard to reverse later.
